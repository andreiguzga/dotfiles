# Worker permissions

Per-task native permission profiles for orchestrator-launched OpenCode workers.

Purpose: cut the routine approval interruptions for edits inside files a task owns
and for the specific check commands the coordinator has already approved, while
leaving every other shell command, every external directory and every destructive,
paid, install, git-write or deploy action behind a native approval prompt.

Verified against OpenCode **1.18.35** (`opencode --version`). Re-verify after an
upgrade: the generator refuses rather than guesses, but the facts below are
version-specific.

## This is an interruption policy, not a sandbox

A permission rule decides whether a human is interrupted. It does not confine the
process. An allowed command still runs with the host user's full filesystem,
process and network authority. Allowing `npm test` approves running whatever that
script does, including code that reaches outside the repository. Approval here means
"we already decided this is worth running", not "this is safe".

## What the profile changes

Generated by `worker_permissions.py`, injected into one worker process only, as
`{"agent":{"build":{"permission":…,"model":…}}}` in `OPENCODE_CONFIG_CONTENT`:

| Key | Rules | Why |
| --- | --- | --- |
| `bash` | `"*": "ask"`, one exact allow per approved command, then inherited denies | unknown commands prompt |
| `edit` | `"*": "ask"`, the owned paths (only with an edit/write model), then inherited denies | owned edits stop interrupting |
| `task` | `"deny"` | a worker cannot recruit subagents |
| `model` | the `--model` value, when given | the edit tool set depends on it |

Nothing else is named. `read`, `external_directory`, `question`, `doom_loop` and the
rest keep their native and inherited rules, including OpenCode's own allows for skill
directories and tool output. No `--auto`, no blanket allow and no global config
change is involved.

### One key covers edit, write and apply_patch

In the installed 1.18.35 bundle, the `edit`, `write` and `apply_patch` tools all call
`ask({permission: "edit", patterns: [path.relative(worktree, file)]})`. That was read
from the tool code shipped in `~/.opencode/bin/opencode`; it is static proof from the
exact installed version, not an observed runtime prompt. The `write` and `apply_patch`
keys are accepted by config and appear in `opencode debug agent build`, but no tool in
this version asks under them, so the profile does not emit them.

### Moves keep their native prompt

Which edit tools a worker gets depends on its model (`ToolRegistry.tools` in the
bundle, confirmed natively through the `tools` field of `debug agent build`): a model
id containing `gpt-` (but not `oss` or `gpt-4`) gets `apply_patch` *instead of*
`edit`/`write`; every other model gets `edit`/`write` and no `apply_patch`.

- **apply_patch models.** A move asks `edit` with the patched file's *source* path,
  exactly like an in-place update of that file; the destination never appears in the
  ask. No permission rule can tell the two apart, and `apply_patch` cannot be disabled
  separately from `edit`. So for these models the profile emits **no edit allows**:
  every apply_patch request prompts, moves included, whether the destination is in an
  owned directory or elsewhere in the repo. Approved bash commands stay allowed.
  The generator enforces this: it drops the edit allows when the native tool set has
  `apply_patch`, and refuses any profile that would combine the two.
- **edit/write models.** These tools cannot rename. A move is a `write` of the new
  file plus a shell `mv`, `git mv` or `rm` of the old one, and those commands are
  restricted (`git mv` and `git rm` included): they can never be approved with
  `--verify`, so they always ask. Writing
  the new copy inside an owned path is allowed (it is a file creation, and the source
  still exists); outside owned paths it asks.
- **No `--model`.** The runtime default model is not visible under `--pure` (a plugin
  may supply it), so it may be an apply_patch model. No edit allows are emitted.

The worker must run the model the profile was generated for: always launch it with
the identical explicit `--model`. The profile also sets `agent.build.model`, and
`debug agent build` resolves to it, but how the TUI picks its model at launch (CLI
flag, agent model or a remembered last-used model) was not verified, so treat the pin
as an unverified extra, not a guarantee. This direction fails **open**: if a worker
under an edit-allowing profile ends up on an apply_patch model (wrong `--model`, or a
model switched inside the TUI by a human), moves of owned files pass without a prompt.

## The generator verifies the native ruleset and fails closed

OpenCode keeps the **last** matching rule. Config sources are deep-merged key by key,
so an inherited per-pattern rule keeps its original position. An inherited
`curl *: allow` after the profile's `"*": "ask"` still wins; an inherited deny before
it is shadowed; an inherited deny before an owned-path allow loses to that allow for
every path both match. Before printing anything the generator therefore runs, in the
task cwd:

```sh
opencode --pure debug config            # plugin list (see below)
opencode --pure debug agent build       # baseline: without the profile
opencode --pure debug agent build       # candidate: with the profile (again if edit
                                        # allows are dropped for apply_patch)
```

It re-asserts every bash and edit **deny** from the baseline after the profile's own
rules, then refuses (non-zero exit, nothing on stdout) unless, for `bash`, `edit` and
`task` in the candidate ruleset:

- the last catch-all rule is the profile default (`ask`, `ask`, `deny`);
- no `allow` follows it except the profile's own exact allows;
- every profile allow follows it and evaluates to `allow` for its own text;
- **every baseline deny pattern is still a deny, and no ask or allow after its last
  occurrence matches any text it matches.** Overlap is decided on the two patterns
  (an exact intersection of OpenCode's `*`/`?` wildcards), not on sample paths, so a
  narrower or broader later allow can never override an inherited deny;
- with `apply_patch` in the tool set, no edit allow exists;
- with `--model`, the build agent resolves to that model.

A deny that cannot be re-asserted is refused outright: one whose pattern is a key the
profile sets itself (`"*"`, or an approved command such as `git status`), and one in
an inherited `agent.build.permission` block that sits before an overlapping owned
allow (its position cannot be moved). Overlapping a deny inside the owned scope is
otherwise fine: `pkg/**` with an inherited `*.env: deny` keeps `pkg/x.env` denied.

A missing binary, a timeout or unparseable output is also a refusal. There is no
override flag. If inherited config conflicts, run that worker without a profile and
answer its prompts.

### Inherited sources this covers

Coverage holds by construction: the check reads the binary's own resolved ruleset, so
every source that `opencode --pure debug agent build` merges is included, whatever it
is. For orientation only, a copy of the config loader source (version not
established) lists: global config (`<XDG_CONFIG_HOME or ~/.config>/opencode/`
`config.json`, `opencode.json`, `opencode.jsonc`), an `OPENCODE_CONFIG` file, project
`opencode.json(c)` files and `.opencode/` directories (including their `agent`
definitions), managed config and managed preferences, and the native agent defaults.
The tests build deny layers in the global config file (via `XDG_CONFIG_HOME`), an
`OPENCODE_CONFIG` file and a project config (top-level and `agent.build`), and check
every deny against the native ruleset. Managed config and managed preferences were
not exercised.

Plugins are **not** loaded under `--pure`, so their effect on the ruleset cannot be
observed there. Instead every plugin OpenCode lists in `plugin_origins` (global and
project, including `.opencode/plugins/` files) is read, and the generator refuses if
any source mentions a `config` hook (which can rewrite permission rules) or a
`permission.ask` hook (which can answer asks), or cannot be located. This is a static
text check, not an execution. Only the entry file of a `file://` plugin is read (the
current ones import only `node:` builtins and types), and every source file of an npm
plugin package; a plugin that builds hook names at runtime, or imports a local module
that defines them, would evade it. The plugins configured at the time of writing (codex auth
4.4.0, the asana schema fix, and the two Herdr plugins) only observe events and pass.

### What the check proves, and what it does not

The preflight proves the ruleset that `opencode --pure debug agent build` reports for
the build agent, in that cwd, at that moment. It does **not** prove runtime parity:

- the worker runs *with* plugins; the plugin gate above is static, not observed;
- no worker is launched and no tool call is observed. That the running worker
  consumes the same `OPENCODE_CONFIG_CONTENT` the check used follows from the worker
  inheriting the pane environment, which was not observed (see Injecting it);
- the tool code facts (the `edit` key, source-only move patterns, tool selection by
  model id) are static reads of the installed bundle, plus the native `tools` field.

### Point in time

The check runs once, when the generator runs. Config is read again when the worker
starts, and nothing re-checks it: a project or global config, plugin or managed
policy changed after generation is not covered, and restarting the worker reuses the
exported variable without regenerating. Regenerate (and restart) whenever the task,
the cwd, the model or any config source changes. An OpenCode upgrade invalidates the
static facts above until they are re-verified.

## Owned paths

Edit asks are matched against `path.relative(worktree, file)`, where `worktree` is the
checkout's `git rev-parse --show-toplevel` (a non-git directory gets `/`). So:

- `--cwd` must be absolute and canonical (exactly its own `realpath`; on macOS that
  means `/private/var/…`, not `/var/…`), and inside a git worktree. A non-git cwd is
  refused.
- `--owned` entries are relative to the cwd, but the emitted patterns are relative to
  the worktree root. From cwd `repo/sub`, `--owned pkg` emits `sub/pkg/**`. A linked
  worktree uses its own root.
- A directory becomes `dir/**`; a file stays an exact path.
- A file that does not exist yet is allowed as an exact path when its parent directory
  already exists. A missing directory is refused; create it first.
- Refused: absolute paths, `~`, `..`, `.git`, the cwd itself (`.`), `*`, `?`, `\`,
  any symlink on the way to the entry, and any symlink inside an owned directory.

OpenCode resolves a tool's path before relativising it, so `pkg/../secret.env` is
matched as `secret.env` and asks.

## Exact command allows

A pattern without `*` is anchored on both ends: `git status` matches only
`git status`, not `git status --short` and not `git statusx`. A trailing `" *"` would
make the arguments optional, which is why the generator never emits one. Each variant
of an approved command therefore asks separately. That is the safe direction, and it
is why a profile with two approved commands still interrupts on a third.

The generator refuses to allow-list:

- shell wrappers: `sh`, `bash`, `zsh`, `eval`, `exec`, `env`, `xargs`, `sudo`,
  `timeout`, `caffeinate` and similar
- inline code (`python -c`, `node -e`), interpreter scripts (`python script.py`), and
  modules outside a known runnable set (`unittest`, `pytest`, `ruff`, `mypy`, …)
- package managers without a reviewable subcommand: `npm run build`, `npm install`,
  `yarn add`, `bun x`, `npx …`
- anything compound, substituted, redirected or piped, globbed arguments, and
  write-inducing options such as `--output`, `-o`, `--exec`
- quoted or oddly spaced commands, and executables given as a path
- restricted commands entirely: git-write, install, publish, deploy and paid services

## Injecting it

```sh
# 1. In the worker pane's shell, in the task cwd, before the agent starts.
#    Clear any earlier profile first: a refusal prints nothing, and eval of nothing
#    would otherwise leave the previous task's allows in place.
unset OPENCODE_PERMISSION OPENCODE_CONFIG_CONTENT
eval "$(python3 ~/.config/herdr/plugins/orchestrator/worker_permissions.py \
  --cwd /absolute/canonical/path/to/worktree \
  --owned herdr/.config/herdr/plugins/orchestrator \
  --verify 'git status' \
  --verify 'python3 -m unittest herdr.test_orchestrator' \
  --model anthropic/claude-sonnet-4-5)"

# 2. Start the worker as before, with the identical --model.
herdr agent start T03-permissions --kind opencode --pane w1:p4 \
  -- --agent build --model anthropic/claude-sonnet-4-5
```

The output is `unset OPENCODE_PERMISSION` plus one `export OPENCODE_CONFIG_CONTENT=…`.
Any `OPENCODE_CONFIG_CONTENT` the pane already had is discarded by the leading
`unset`. Both are set in the pane shell, so only processes started from it inherit
them. `herdr agent start --help` says it starts the agent from the pane's
interactive shell prompt, which implies the worker inherits that shell's environment;
a live launch was not observed (if it did not inherit, the profile would simply not
apply and the worker would prompt as usual). The worker must start in the same cwd
the profile was verified for. The generator writes no files and starts no worker. If it refuses, the
leading `unset` has already cleared any earlier profile; start the worker without
one.

`--auto` is never used. Native approval dialogs stay live and the supervisor still
never answers them.

## Known limitations

- **The evaluator normalises commands.** The shell tool parses the command with
  tree-sitter and asks once per sub-command, so `pwd && ls` is two asks. A
  `redirected_statement` is matched as its full text. Exact-string approval reduces
  interruptions; it does not enforce exact-string execution.
- **`always` grants are coarser.** Answering "always" in the TUI remembers a prefix
  rule such as `git *` in memory, after the config rules, for the rest of that
  process. That is a human decision at a pane; a restart drops it.
- **apply_patch workers get no edit scope.** Because moves cannot be told apart from
  updates (see Moves keep their native prompt), every edit by a GPT-family worker
  prompts under a profile; only its approved commands stop interrupting.
- **Debug side effects.** `opencode debug agent build` records the task directory as
  a project in OpenCode's local database (`~/.local/share/opencode`), as launching the
  worker there would anyway. It makes no model call. The tests point `XDG_DATA_HOME`
  at each fixture so they add no rows to the real database.

## Startup and restart effects

- Config is read when the OpenCode process starts. A changed profile needs the worker
  restarted; a new turn in the same process will not pick it up.
- A restart reuses the exported variable; it does not regenerate or re-check it (see
  Point in time).
- Two workers in different panes get independent profiles.
- No config file is modified, so sessions launched without these variables behave
  exactly as before.

## Verifying

```sh
python3 ~/.config/herdr/plugins/orchestrator/worker_permissions.py --cwd … --owned … --show
python3 -m unittest discover -s herdr -p 'test*.py' -q
```

`--show` prints the cwd, the worktree root, the model and its edit tools, the allows
and the re-asserted denies to stderr. The tests build throwaway git fixtures and read
the real binary's ruleset: a hostile project config with inherited `curl *` and
`secret.env` allows, global- and project-scope inherited deny layers, a project plugin
with a `config` hook, and apply_patch and edit/write models. They make no model call
and skip the native cases when `opencode` is not installed. They exercise the
permission ruleset, not a running worker.

`--list-safe` prints commonly read-only commands. They are a **reference only** and
are never auto-allowed; each command enters a profile solely because the coordinator
named that exact string in the task brief.
